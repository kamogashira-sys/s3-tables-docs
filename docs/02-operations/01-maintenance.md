## 概要

Amazon S3 Tablesは、Apache Icebergテーブルのパフォーマンスと効率性を維持するための自動メンテナンス機能を提供します。メンテナンス機能は以下の3つの主要な操作で構成されています：

1. **コンパクション（Compaction）**: 小さなファイルを結合し、クエリパフォーマンスを向上
2. **スナップショット管理（Snapshot Management）**: 古いスナップショットを削除し、ストレージコストを削減
3. **未参照ファイル削除（Unreferenced File Removal）**: テーブルメタデータから参照されていないファイルを削除

これらのメンテナンス操作は、Table BucketレベルまたはTableレベルで設定でき、自動的に実行されます。

## メンテナンス設定レベル

### Table Bucketレベル
- Table Bucket内のすべてのTableに適用されるデフォルト設定
- 新しく作成されるTableは自動的にこの設定を継承
- 既存のTableには影響しない

### Tableレベル
- 個別のTableに対する設定
- Table Bucketレベルの設定を上書き可能
- より細かい制御が必要な場合に使用

## コンパクション（Compaction）

### 概要
コンパクションは、小さなデータファイルを大きなファイルに結合することで、クエリパフォーマンスを向上させる操作です。多数の小さなファイルは、クエリ時のオーバーヘッドを増加させるため、定期的なコンパクションが推奨されます。

### コンパクション戦略

S3 Tablesは4種類のコンパクション戦略をサポートしています：

#### 1. Auto（自動選択）
- **デフォルト戦略**
- テーブルの`sort_order`プロパティの有無に基づいて自動的に戦略を選択
  - `sort_order`が設定されている場合: Sort戦略を使用
  - `sort_order`が設定されていない場合: Binpack戦略を使用
- 推奨される戦略（ほとんどのユースケースに適合）

#### 2. Binpack（ビンパッキング）
- 小さなファイルを結合して大きなファイルを作成
- データの並び順は変更しない
- 最もシンプルで高速なコンパクション
- ソート順が重要でない場合に適している

#### 3. Sort（ソート）
- 指定された列に基づいて階層的にデータをソート
- クエリパフォーマンスの向上（特にフィルタリングクエリ）
- ソート列を使用したクエリで効果的
- 単一列または複数列でのソートをサポート

#### 4. Z-order（Z次元最適化）
- 複数の列を使用した多次元クラスタリング
- 複数の列でフィルタリングするクエリに最適
- Sort戦略よりも複雑だが、多次元クエリで高いパフォーマンス
- 最大4列までサポート

### コンパクション設定パラメータ

```json
{
  "enabled": true,
  "targetFileSizeMB": 512
}
```

| パラメータ | デフォルト値 | 最小値 | 説明 |
|-----------|------------|--------|------|
| `enabled` | true | - | コンパクションの有効/無効 |
| `targetFileSizeMB` | 512 | 64 | ターゲットファイルサイズ（MB） |

### コンパクションの制限事項

#### サポートされるファイル形式
- Parquet（デフォルト出力形式）
- Avro
- ORC

#### サポートされない機能
- **データ型**: Fixed型
- **圧縮形式**: brotli、lz4

#### 同時実行制御
- 楽観的同時実行制御（Optimistic Concurrency Control）を使用
- 同時書き込みが発生した場合、競合の可能性あり
- 競合が発生した場合、メンテナンスジョブは失敗する可能性

### 必要な権限

Sort戦略およびZ-order戦略を使用する場合、以下の追加権限が必要：
- `s3tables:GetTableData`

## スナップショット管理（Snapshot Management）

### 概要
スナップショット管理は、古いスナップショットを自動的に削除し、ストレージコストを削減する機能です。各スナップショットはテーブルの特定時点の状態を表し、時間とともに蓄積されます。

### スナップショット保持ポリシー

スナップショットは以下の2つの条件を**両方とも満たす**場合に削除されます：

1. **最小スナップショット数**: 指定された数以上のスナップショットが存在する
2. **最大保持期間**: スナップショットの作成時刻が保持期間を超えている

### スナップショット管理設定パラメータ

```json
{
  "enabled": true,
  "minimumSnapshots": 1,
  "maximumSnapshotAge": 120
}
```

| パラメータ | デフォルト値 | 最小値 | 説明 |
|-----------|------------|--------|------|
| `enabled` | true | - | スナップショット管理の有効/無効 |
| `minimumSnapshots` | 1 | 1 | 保持する最小スナップショット数 |
| `maximumSnapshotAge` | 120時間 | 1時間 | スナップショットの最大保持期間 |

### スナップショット管理の制限事項

#### サポートされない機能
- **ブランチベース保持ポリシー**: Icebergのブランチ機能を使用した保持ポリシーは非サポート
- **タグベース保持ポリシー**: Icebergのタグ機能を使用した保持ポリシーは非サポート
- **metadata.json設定**: テーブルの`metadata.json`ファイルで設定された保持ポリシーは無視される

#### 自動無効化条件
以下の条件でスナップショット管理が自動的に無効化される場合があります：
- ブランチまたはタグが存在する場合
- カスタム保持ポリシーが`metadata.json`に設定されている場合

## 未参照ファイル削除（Unreferenced File Removal）

### 概要
未参照ファイル削除は、テーブルメタデータから参照されていないデータファイルを自動的に削除する機能です。これらのファイルは、失敗したトランザクションや削除されたスナップショットから残されたものです。

### 削除対象ファイル

以下の条件を満たすファイルが削除対象となります：

1. **未参照ファイル**: 現在のテーブルメタデータから参照されていない
2. **保持期間超過**: ファイルの作成時刻が保持期間を超えている

### 未参照ファイル削除設定パラメータ

```json
{
  "enabled": true,
  "unreferencedDays": 3,
  "nonCurrentDays": 10
}
```

| パラメータ | デフォルト値 | 最小値 | 説明 |
|-----------|------------|--------|------|
| `enabled` | true | - | 未参照ファイル削除の有効/無効 |
| `unreferencedDays` | 3日 | 1日 | 未参照ファイルの保持期間 |
| `nonCurrentDays` | 10日 | 1日 | 非現行バージョンファイルの保持期間 |

### 注意事項

- **タイムトラベルクエリへの影響**: 保持期間を短く設定すると、過去のデータにアクセスできなくなる可能性
- **安全マージン**: デフォルト値（3日）は、ほとんどのユースケースで安全なマージンを提供
- **長期保持**: コンプライアンス要件がある場合は、保持期間を延長することを推奨

## メンテナンスジョブのステータス確認

### ステータスの種類

メンテナンスジョブは以下のステータスを持ちます：

| ステータス | 説明 |
|-----------|------|
| `Successful` | メンテナンスジョブが正常に完了 |
| `Failed` | メンテナンスジョブが失敗 |
| `Disabled` | メンテナンスが無効化されている |
| `Not_Yet_Run` | メンテナンスジョブがまだ実行されていない |

### ステータス確認方法

#### AWS CLI
```bash
# Table Bucketのメンテナンス設定を確認
aws s3tables get-table-bucket-maintenance-configuration \
  --table-bucket-arn arn:aws:s3tables:region:account-id:bucket/table-bucket-name

# Tableのメンテナンス設定を確認
aws s3tables get-table-maintenance-configuration \
  --table-bucket-arn arn:aws:s3tables:region:account-id:bucket/table-bucket-name \
  --namespace namespace-name \
  --name table-name
```

### 必要な権限

メンテナンス設定の確認には以下の権限が必要：
- `s3tables:GetTableMaintenanceConfiguration`
- `s3tables:GetTableBucketMaintenanceConfiguration`

メンテナンス設定の変更には以下の権限が必要：
- `s3tables:PutTableMaintenanceConfiguration`
- `s3tables:PutTableBucketMaintenanceConfiguration`

## CloudTrailによる監視

### CloudTrailイベント

S3 Tablesのメンテナンス操作は、AWS CloudTrailで記録されます。

#### イベントソース
- `s3tables.amazonaws.com`

#### メンテナンスイベントタイプ
- `TablesMaintenanceEvent`

#### アクティビティタイプ

| アクティビティタイプ | 説明 |
|------------------|------|
| `IcebergCompaction` | コンパクション操作 |
| `IcebergSnapshotManagement` | スナップショット管理操作 |

### CloudTrailログの例

```json
{
  "eventVersion": "1.08",
  "userIdentity": {
    "type": "AWSService",
    "invokedBy": "s3tables.amazonaws.com"
  },
  "eventTime": "2024-12-01T10:00:00Z",
  "eventSource": "s3tables.amazonaws.com",
  "eventName": "TablesMaintenanceEvent",
  "awsRegion": "us-east-1",
  "requestParameters": {
    "tableBucketArn": "arn:aws:s3tables:us-east-1:123456789012:bucket/my-table-bucket",
    "namespace": "my-namespace",
    "tableName": "my-table",
    "activityType": "IcebergCompaction"
  },
  "responseElements": {
    "status": "Successful"
  }
}
```

### 監視のベストプラクティス

1. **CloudWatch Logsとの統合**
   - CloudTrailログをCloudWatch Logsに送信
   - メトリクスフィルターを作成して失敗イベントを監視

2. **アラート設定**
   - メンテナンスジョブの失敗時にSNS通知を送信
   - 連続した失敗を検出するアラームを設定

3. **ログ分析**
   - CloudWatch Logs Insightsを使用してメンテナンス履歴を分析
   - パフォーマンストレンドを追跡

## メンテナンス設定のベストプラクティス

### 1. デフォルト設定の活用

ほとんどのユースケースでは、デフォルト設定が適切です：
- コンパクション: Auto戦略、512MB ターゲットファイルサイズ
- スナップショット管理: 最小1スナップショット、120時間保持
- 未参照ファイル削除: 3日保持

### 2. ワークロードに応じた調整

#### 高頻度書き込みワークロード
- コンパクション頻度を増やす
- ターゲットファイルサイズを調整（例: 256MB）
- 未参照ファイル削除の保持期間を短縮（例: 1日）

#### 分析ワークロード
- Sort戦略またはZ-order戦略を使用
- よく使用されるフィルタ列をソート列として指定
- ターゲットファイルサイズを大きく設定（例: 1024MB）

#### コンプライアンス要件がある場合
- スナップショット保持期間を延長（例: 720時間 = 30日）
- 未参照ファイル削除の保持期間を延長（例: 30日）
- 最小スナップショット数を増やす（例: 10）

### 3. パフォーマンスモニタリング

- CloudTrailログでメンテナンスジョブの実行時間を追跡
- クエリパフォーマンスの改善を測定
- ストレージコストの削減を追跡

### 4. テスト環境での検証

- 本番環境に適用する前に、テスト環境で設定を検証
- 異なる戦略のパフォーマンスを比較
- ワークロードに最適な設定を特定

## トラブルシューティング

### メンテナンスジョブが失敗する

#### 原因1: 同時書き込み競合
- **症状**: コンパクションジョブが`Failed`ステータス
- **原因**: 楽観的同時実行制御による競合
- **対策**:
  - 書き込み頻度を調整
  - メンテナンスウィンドウを設定
  - 再試行を待つ（自動的に再試行される）

#### 原因2: 権限不足
- **症状**: メンテナンスジョブが`Failed`ステータス
- **原因**: Sort/Z-order戦略で`s3tables:GetTableData`権限が不足
- **対策**: 必要な権限を付与

#### 原因3: サポートされないデータ型
- **症状**: コンパクションジョブが`Failed`ステータス
- **原因**: Fixed型データまたはbrotli/lz4圧縮を使用
- **対策**:
  - サポートされるデータ型に変換
  - サポートされる圧縮形式を使用

### スナップショット管理が無効化される

#### 原因: ブランチまたはタグの存在
- **症状**: スナップショット管理が`Disabled`ステータス
- **原因**: テーブルにブランチまたはタグが存在
- **対策**:
  - ブランチ/タグを削除
  - または手動でスナップショット管理を実施

### ストレージコストが削減されない

#### 原因: 保持期間が長すぎる
- **症状**: 未参照ファイルが削除されない
- **原因**: `unreferencedDays`または`nonCurrentDays`が長すぎる
- **対策**: 保持期間を短縮（ただし、タイムトラベルクエリへの影響を考慮）

## まとめ

S3 Tablesのメンテナンス機能は、Apache Icebergテーブルのパフォーマンスとコスト効率を自動的に最適化します。以下のポイントを押さえることで、効果的なメンテナンス戦略を実装できます：

1. **デフォルト設定から開始**: ほとんどのユースケースで適切
2. **ワークロードに応じて調整**: 書き込みパターンとクエリパターンを考慮
3. **監視とアラート**: CloudTrailとCloudWatch Logsで継続的に監視
4. **定期的な見直し**: パフォーマンスとコストを定期的に評価し、設定を最適化
